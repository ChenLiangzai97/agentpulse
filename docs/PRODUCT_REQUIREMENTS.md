# AgentPulse 产品需求与设计记录

更新：2026-10-18。本文是后续需求讨论的统一入口，持续增补，不以聊天记录作为唯一依据。

状态约定：**用户确认**是用户明确表达的目标；**设计建议**尚非最终决定；**待确认**须继续讨论；**实现待验收**不能写成已完成。本文描述产品终态，不代表当前版本已具备全部能力。

## 1. 产品范围与推进原则

### 用户确认

近期集中完善两项核心功能：
1. **集中管理**：集中查看和操作不同机器上的 Agent 会话，优先完善 OpenCode 体验。
2. **日志总结**：既供个人回顾每天工作，也能生成发给团队的日报。

任务编排暂不推进。将来需要时，先调研现成开源方案再决定，不在本轮自行扩展成任务调度平台。

短期可以会话优先；未来希望增加待办事项，并支持项目优先，或提供两种视图。用户曾提出一个事项可能就是一个项目，其最终业务建模尚未确定。

### 设计建议，待未来阶段确认

会话视图与项目视图使用同一批数据。Project作为长期工作空间、事项作为工作目标、Session作为执行对话，可以一事项关联多个会话；这个区分是设计建议，不是已确认的数据模型。本轮不提前实现完整事项/编排体系。

## 2. 集中管理：用户明确的终态

用户原意：
> AgentPulse 的每个页签就是一个 OpenCode 会话，可以直接在 AgentPulse 里跟 Agent 对话，并无痛使用 CLI 命令，比如 /model、/new、/fork、/session；历史会话可以无痛接手；AgentPulse 不小心关掉时 Agent 仍继续工作，除非显式要求停止；支持跨机管理。

### CM-01 会话页签

- 一个页签对应一个OpenCode会话，直接展示对话、工具调用与结果、输入框和待处理交互。
- 在多个会话间切换，不需要反复进入模板或启动详情才能工作。
- 设计建议：页签保留各自草稿、滚动位置、未读与审批提醒；关闭页签只是收起界面，不停止执行。

### CM-02 接近原生的命令体验

- 支持 /model、/new、/fork、/session 等常用操作，命令实际效果与界面反馈一致。
- /model：选择与执行实际模型一致，不能只改显示；选择本身不应产生多余推理轮次。
- /new：新建会话并进入新页签。
- /session：选择与切换历史会话，保留其真实身份和上下文。
- /fork：真正继承对应历史上下文，创建可独立继续对话的分支；不以“历史拼一条prompt”或空会话冒充。
- 相关实施范围还包含 /agent、/help 和经验证的原生自定义命令。
- TUI内置动作与服务端自定义命令不必具有相同API；需映射并验证，未知命令不能静默当普通prompt发送。
- 设计建议：/fork新分支开新页签；默认分叉完整对话。指定消息的边界按本机实际语义说明。对话分叉不等于Git/worktree隔离，同目录文件仍可能共享。

### CM-03 历史会话接续

- 用户要求能够无痛接手历史会话继续工作，而非仅观察或手动复制历史。
- 需要保留真实上下文、工作目录和有效配置，并明确当前执行主机及运行状态。
- **待确认关键边界**：历史接续是否包括BotMux驱动的会话？普通终端历史、仍在运行的终端会话、BotMux会话，是否采用不同接入/交接策略？
- 旧阶段已批准并实现的约束是“外部/BotMux/legacy永久只观察，仅AgentPulse自建绑定可控”。最新历史接续目标与此存在冲突。**不能因记录新目标就解除现有保护**；须用户明确范围后制定来源验证与控制权交接设计。
- 设计建议：已有AgentPulse会话恢复连接；普通终端会话显式接入；BotMux会话若纳入，需防止两个驱动端同时控制。不可直接以metadata或管理员身份提权。

### CM-04 执行生命周期独立

- 用户要求：AgentPulse意外关闭不应导致Agent停止，只有显式要求停止才停止。
- 设计解释待细化：应覆盖关闭页签/浏览器、中央Server暂时退出或重启；执行主机上的Agent运行与界面/中央连接解耦。
- 设计建议：重新连接后补齐输出、状态和交互；区分“中止本轮”“停止会话”“停止整个实例”。
- 待明确：执行主机重启、Agent原生进程崩溃、Supervisor退出时的恢复保证；不能把原生不支持的pending交互跨进程恢复承诺成已具备。

### CM-05 跨机管理

- 集中管理多台机器上的会话，能够对相应主机上的Agent对话和操作。
- 设计建议：会话明确显示主机与目录；主机断线显示连接故障而非任务完成；断线后补采，不盲重发不确定是否执行的消息。
- 多主机路径不能仅凭目录字符串随机路由；鉴权、主机能力与来源校验持续有效。

## 3. 已授权的近期体验优化

### UX-01 完整汉化

菜单栏、桌面与移动导航、按钮、状态、提示、错误和空态中文完整，避免产品界面中英混杂。技术名、模型名、原生命令和用户内容保留原意。

实施要求：沿用现有i18n层，词条集中到zh-CN/en字典，保留语言切换，不把硬编码英文替换为散落中文。

### UX-02 新建会话不依赖模板

- 用户认为启动放在Template里很迷惑，选项过多。
- 主入口直接新建会话，常规只需Agent与目录，有效默认值消化底层配置。
- 日常设置尽可能通过对话内 /命令完成。
- 模板保留为高级预设，不要求先保存模板；首次缺主机/profile/凭据时明确引导，不伪装成功。
- 实施细节与验收见 [SESSION_UX_OPTIMIZATION_SPEC.md](SESSION_UX_OPTIMIZATION_SPEC.md)。

## 4. 日志总结

### 用户确认

个人日常回顾和可发给团队的日报**两者都需要**。

### 设计建议：统一事实记录，两种呈现

**个人回顾**：按日期/项目浏览目标、实际操作、尝试与决策、验证结果和未完成项；可以展开定位原始消息和工具证据。

**团队日报**：从同一记录提炼成果、进行中、阻塞与下一步；省略重复调试与内部上下文，可编辑、复制或投递。

建议流程：自动采集 → 整理工作事实 → 个人回顾 → 团队日报草稿 → 预览编辑 → 发送/投递。是否默认自动发送尚未确认，不因本需求记录自动对外投递。

### 建议的质量与数据规则，后续需具体设计

- 助手自述、实际执行、已验证成果、待验证项分开；Agent停止生成不等于业务完成。
- 多会话关联同一工作时合理归组，不能未经证据就合并不同工作。
- 分叉继承历史不重复计入新工作、费用或日报；跨天只计当日新增活动。
- 隐藏运行上下文不参与摘要，实际交付工具证据保留。
- 用户编辑不被重新生成无提示覆盖；已发送版本留档。
- 团队版有范围选择与敏感内容处理，不默认发布私人会话、凭据或内部敏感路径。
- 可回溯来源，生成失败、配置缺失、预算限制要明确显示。

待细化：日报模板、默认时区/统计区间、个人与团队可见范围、投递目标、自动化程度、编辑与重新生成策略。

## 8. 探索方向：AgentPulse 是否承担 BotMux 的会话驱动角色

2026-10-18 用户提出：AgentPulse能否充当BotMux的角色，从而规避两者同时驱动会话的冲突。**状态：探索/待评估，不是已批准替换BotMux。**

设计建议：由执行主机上的统一会话控制服务作为唯一执行权源，Web、CLI接入和飞书作为入口。飞书消息映射到既有会话，Agent输出与审批回传飞书；不同入口共享历史、有效配置和交互状态。应区分“接替会话驱动职责”和“复刻整个BotMux产品”，近期只讨论前者，不因此启动多机器人项目编排。

预期收益：同一会话不再由两个独立系统重复发送prompt或回答审批；网页和飞书只是同一控制服务的客户端。仅增加飞书适配器并不能自动消除冲突，前提是BotMux等旧驱动明确停止对已交接会话的写入。

必须评估：飞书身份与平台用户授权映射、群/话题到会话的绑定、重复消息去重、并发入口排队/中止优先级、审批唯一回答与撤销、多机执行身份、输出和附件回传、网络断线补偿、审计、守护进程生命周期、历史原生会话发现与续接能力，以及原BotMux功能的差距。

迁移原则建议：先给AgentPulse新建会话提供Web+飞书双入口，再对非活跃或明确交接的旧会话验证接入；不静默接管BotMux运行中的会话，不以metadata授权。已有运行环境与插件维持原样直至具体迁移方案获批。

待讨论：用户期望只替代“飞书↔Agent会话桥接”，还是也包含BotMux的多bot身份、路由、附件、定时任务、交接协作等完整能力？后者涉及更大产品范围，需先调研与列能力矩阵。
